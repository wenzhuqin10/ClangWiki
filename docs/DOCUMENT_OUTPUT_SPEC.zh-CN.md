# ClangWiki 文档输出规范

## 1. 目的

本规范定义 ClangWiki 通过 `opencode run` 和 GLM-5.1 生成 Markdown Wiki 时必须遵守的文档类型、章节顺序、证据等级和质量门禁。

本版本不包含 RAG、Embedding 或向量检索。文档内容只能来自 Clang 分析产物、任务上下文中附带的源码，以及 OpenCode 在只读权限下能够访问的目标仓库文件。

## 2. 文档分层

```text
仓库级
├── README.md
└── Architecture.md

模块级
└── Modules/<module>.md

事实参考级
├── DataStructures.md
├── CallFlows.md
└── APIReference.md
```

- 仓库级文档回答系统由什么组成、模块如何协作。
- 模块级文档服务领域任务理解、故障定位和代码修改，是 Wiki 的核心。
- 事实参考级文档提供符号、字段、调用边和源码位置，避免模块文档重复堆砌 API。

## 3. 通用输出契约

每篇文档必须满足以下要求：

1. 以一个一级标题开始。
2. 严格按照任务上下文给出的顺序输出二级章节。
3. 不得改名、遗漏、合并或增加二级章节。
4. 可以在二级章节内部使用三级及更深层级标题。
5. 标识符、文件路径、类型、宏和参数名必须保持源码原样。
6. 重要结论应附带 `文件路径:行号` 或明确的符号位置。
7. 证据不足时仍保留章节，明确说明无法确认的内容和所需材料。
8. 不得用通用协议知识替代当前仓库的实际实现证据。
9. `POSSIBLE_CALL` 和 `certainty=lexical` 不得写入确定调用链。
10. 只输出最终 Markdown 正文，不输出生成过程或外层代码围栏。

## 4. 证据等级

| 等级 | 来源 | 允许的表述 |
|---|---|---|
| 编译器确认 | Clang AST、类型绑定、确定关系 | “Clang 分析确认……” |
| 源码确认 | 源码中的赋值、分支、日志、资源操作 | “源码显示……” |
| 合理推断 | 命名、目录或多条关系的综合解释 | “根据现有证据推测……” |
| 无法确认 | 缺少运行数据、设计文档或完整关系 | “当前证据无法确定……” |

合理推断不得写成确定事实。设计原因、运行时顺序、线程安全和故障根因尤其需要遵守这一规则。

## 5. 模块文档章节

`Modules/<module>.md` 必须包含：

1. 模块概述；
2. 职责与边界；
3. 领域定位与设计约束；
4. 系统交互与接口关系；
5. 核心任务流程；
6. 状态、事件与时序；
7. 核心实现；
8. 配置、宏与运行变体；
9. 调试与故障定位；
10. Agent 开发导航；
11. 证据、限制与待确认项。

模块文档不应退化为函数列表。它需要先说明模块定位和协作关系，再说明流程、状态和实现，最后给出调试与修改导航。

### 5.1 调试内容

调试章节应按以下结构组织：

```text
故障现象
→ 首先检查的入口或状态
→ 关键字段、返回值或分支
→ 源码、日志或断点位置
→ 确认或排除根因的方法
```

没有实际日志证据时，不得虚构日志名称、错误码或 Trace。

### 5.2 开发导航

开发导航应说明：

- 常见修改入口；
- 直接影响的文件、函数和结构体；
- 潜在上下游影响；
- 接口、时序、并发、内存和性能风险；
- 建议执行的单元、集成和回归测试。

代码直接证明的影响和推断的潜在影响必须分开表达。

## 6. 其他文档章节

### 6.1 README.md

项目简介、代码版本与分析范围、系统组成、模块导航、核心任务流程导航、数据结构与 API 导航、推荐阅读顺序、证据说明、已知覆盖限制。

### 6.2 Architecture.md

系统目标与边界、总体模块分层、模块职责、模块依赖、跨模块接口、核心数据流、核心调用流程、状态与时序关系、构建配置与运行变体、架构风险与证据限制。

### 6.3 DataStructures.md

范围与索引、核心结构体、枚举与类型别名、初始化与生命周期、读写与传递关系、配置与消息映射、证据与待确认字段。

### 6.4 CallFlows.md

流程索引、触发条件与前置状态、确定调用链、数据与配置传播、分支与失败路径、时序与并发关系、候选调用与未解析关系、源码证据与覆盖限制。

### 6.5 APIReference.md

API 索引、函数签名与位置、参数与返回值、调用者与被调用者、副作用与状态要求、错误处理、配置与条件编译、证据与限制。

## 7. 缺失信息的标准写法

固定章节不代表强制生成不存在的内容。建议使用以下写法：

```markdown
## 状态、事件与时序

当前静态分析结果未发现能够确认的状态迁移、定时器或中断关系。需要结合运行日志、调度配置或设计文档进一步确认。
```

不允许使用没有仓库证据的通用描述填充章节。

## 8. 自动质量门禁

ClangWiki 在保存输出前检查：

- 输出长度满足最低要求；
- 存在 Markdown 一级标题；
- 代码围栏闭合；
- 二级章节与文档类型的 Schema 完全一致；
- 章节顺序正确；
- 每个必需章节均有正文；
- 输出不是 OpenCode 错误信息。

任一检查失败时，本次文档任务失败，原始标准输出和错误输出保留在 workspace 日志目录中，不写入不符合契约的最终文档。

## 9. 与 Benchmark 的对应关系

| Benchmark 能力 | 主要证据章节 |
|---|---|
| 模块理解 | 模块概述、职责与边界 |
| 接口和跨模块关系 | 系统交互与接口关系、APIReference |
| 调用链恢复 | 核心任务流程、CallFlows |
| 时序分析 | 状态、事件与时序 |
| 故障定位 | 调试与故障定位 |
| 修改规划 | Agent 开发导航 |
| 幻觉控制 | 证据、限制与待确认项 |

因此，后续评测应检查文档是否提高代码定位、调用链恢复、故障诊断和修改规划能力，而不应只评价语言流畅度或篇幅。
