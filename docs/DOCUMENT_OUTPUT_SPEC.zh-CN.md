# ClangWiki 文档输出规范

## 1. 目的

本规范定义 ClangWiki 通过 `opencode run` 和 GLM-5.1 生成 Markdown Wiki 时必须遵守的文档类型、章节顺序、证据等级和质量门禁。

文档内容只能来自 Clang 分析产物、任务上下文中的源码和已生成子文档，以及 OpenCode 在只读权限下能够访问的目标仓库文件。RAG 负责后续检索与问答，不能代替 Clang 事实生成叶子文档。

## 2. 文档分层

```text
仓库导航级
├── README.md                    # repository-guide
└── Architecture.md              # repository-architecture

层级知识路径
└── Modules/<source-path>/index.md
    ├── subsystem-guide          # 子系统导航
    ├── channel-playbook         # 信道任务手册
    └── leaf-engineering         # 叶子工程知识

事实参考级
├── DataStructures.md
├── CallFlows.md
└── APIReference.md
```

- 仓库导航文档是 Agent 的首读入口，负责把用户任务路由到正确技术域。
- 子系统文档继续缩小范围，信道文档恢复端到端业务并路由到功能叶子。
- 叶子工程文档建立领域知识、代码实现、调试和修改验证之间的映射。
- 事实参考级文档提供符号、字段、调用边和源码位置，避免模块文档重复堆砌 API。

## 3. 通用输出契约

每篇文档必须满足以下要求：

1. 以一个一级标题开始。
2. 严格按照任务上下文给出的顺序输出二级章节。
3. 不得改名、遗漏、合并或增加二级章节。
4. 可以在二级章节内部使用三级及更深层级标题。
5. 标识符、文件路径、类型、宏和参数名必须保持源码原样。
6. 重要结论应附带 `文件路径:行号` 或明确的符号位置。
7. 证据不足时仍保留章节，明确说明无法确认的内容和所需材料。
8. 不得用通用协议知识替代当前仓库的实际实现证据。
9. `POSSIBLE_CALL` 和 `certainty=lexical` 不得写入确定调用链。
10. 只输出最终 Markdown 正文，不输出生成过程或外层代码围栏。

## 4. 证据等级

| 等级 | 来源 | 允许的表述 |
|---|---|---|
| 编译器确认 | Clang AST、类型绑定、确定关系 | “Clang 分析确认……” |
| 源码确认 | 源码中的赋值、分支、日志、资源操作 | “源码显示……” |
| 合理推断 | 命名、目录或多条关系的综合解释 | “根据现有证据推测……” |
| 无法确认 | 缺少运行数据、设计文档或完整关系 | “当前证据无法确定……” |

合理推断不得写成确定事实。设计原因、运行时顺序、线程安全和故障根因尤其需要遵守这一规则。

## 5. 分层专用文档架构

ClangWiki 自底向上生成、供 Agent 自顶向下阅读。所有层级共享机器可读元数据和框架生成的导航卡，但正文不再强制使用同一九章。

### 5.1 仓库导航 `repository-guide`

1. 仓库定位与分析范围；
2. 快速任务导航；
3. 系统分层与模块地图；
4. 仓库级关键业务流程；
5. 公共接口与共享数据；
6. 构建、运行与配置变体；
7. 分析覆盖与证据限制。

它是 Agent 的首读入口，主要回答“应当去哪里”，不得写成全仓源码摘要。

### 5.2 子系统导航 `subsystem-guide`

1. 子系统定位与职责边界；
2. 子模块导航；
3. 入口、出口与接口契约；
4. 跨模块主流程；
5. 状态、时序与资源约束；
6. 故障现象导航；
7. 跨模块修改影响；
8. 证据边界与继续阅读。

它把仓库级任务继续路由到信道或功能模块，重点是任务路由和故障现象路由。

### 5.3 信道任务手册 `channel-playbook`

1. 信道定位与处理目标；
2. 功能子模块地图；
3. 端到端业务流程；
4. 输入输出与数据契约；
5. 配置与协议参数传播；
6. 状态、HARQ与时序；
7. 故障定位决策树；
8. 开发任务路由；
9. 继续下钻与证据限制。

PDSCH、PUSCH 等信道使用这一契约。它恢复端到端业务，但把局部实现链接到下一层功能叶子。

### 5.4 叶子工程文档 `leaf-engineering`

1. 功能目标与责任边界；
2. 领域原理与实现约束；
3. 源码地图；
4. 执行流程与调用链；
5. 数据结构与字段语义；
6. 配置、宏与运行模式；
7. 状态、时序与资源生命周期；
8. 异常路径与故障定位；
9. 修改指南与影响分析；
10. 测试与验证；
11. 相关文档与证据限制。

叶子直接依据 Clang 事实和有界源码，是 Agent 进入目标代码前的最深工程知识单元。

### 5.5 确定性导航卡

框架在每篇文档一级标题后自动加入文档角色、当前位置、父级文档、直接子文档数量和直接源码范围。导航卡不属于二级章节，不由模型自由生成。

### 5.6 后端知识库目录

生成快照写入运行目录后，Wiki 入库会再建立一份按模块隔离的知识文档副本。模块文档不能全部平铺在同一个知识目录中：

```text
repositories/<repo-id>/runs/<run-id>/knowledge/documents/
├── repository/
    ├── Architecture.md
    └── README.md
├── subsystems/<module-id>/index.md
├── channels/<module-id>/index.md
├── modules/<module-id>/index.md
└── facts/
    ├── DataStructures.md
    ├── CallFlows.md
    └── APIReference.md
```

`documents` 表中的 `module_id`、`storage_path` 和 `module_folder` 必须与该目录一致；切块进入 FTS、向量和图谱检索时保留相同元数据。这样同一仓库不同信道或子模块的文档既能独立读取、重建索引和追溯版本，也能在集合级检索时按模块过滤。机器生成快照仍然不可变，源码目录不复制、不修改。

### 5.7 调试内容

调试章节应按以下结构组织：

```text
故障现象
→ 首先检查的入口或状态
→ 关键字段、返回值或分支
→ 源码、日志或断点位置
→ 确认或排除根因的方法
```

没有实际日志证据时，不得虚构日志名称、错误码或 Trace。

### 5.8 开发导航

开发导航应说明：

- 常见修改入口；
- 直接影响的文件、函数和结构体；
- 潜在上下游影响；
- 接口、时序、并发、内存和性能风险；
- 建议执行的单元、集成和回归测试。

代码直接证明的影响和推断的潜在影响必须分开表达。

## 6. 事实参考与仓库架构

### 6.1 Architecture.md

系统目标与边界、总体模块分层、模块职责、模块依赖、跨模块接口、核心数据流、核心调用流程、状态与时序关系、构建配置与运行变体、架构风险与证据限制。

### 6.2 DataStructures.md

范围与索引、核心结构体、枚举与类型别名、初始化与生命周期、读写与传递关系、配置与消息映射、证据与待确认字段。

### 6.3 CallFlows.md

流程索引、触发条件与前置状态、确定调用链、数据与配置传播、分支与失败路径、时序与并发关系、候选调用与未解析关系、源码证据与覆盖限制。

### 6.4 APIReference.md

API 索引、函数签名与位置、参数与返回值、调用者与被调用者、副作用与状态要求、错误处理、配置与条件编译、证据与限制。

## 7. 缺失信息的标准写法

固定章节不代表强制生成不存在的内容。建议使用以下写法：

```markdown
## 状态与时序

当前静态分析结果未发现能够确认的状态迁移、定时器或中断关系。需要结合运行日志、调度配置或设计文档进一步确认。
```

不允许使用没有仓库证据的通用描述填充章节。

## 8. 自动质量门禁

ClangWiki 在保存输出前检查：

- 输出长度满足最低要求；
- 存在 Markdown 一级标题；
- 代码围栏闭合；
- 二级章节与文档类型的 Schema 完全一致；
- 章节顺序正确；
- 每个必需章节均有正文；
- 输出不是 OpenCode 错误信息。
- 仓库、子系统、信道和架构综合文档不包含从子文档机械复制的长段落；
- 综合文档在其专用导航章节中包含本次可用的直接子文档链接；
- 一级标题后存在框架生成的导航卡；
- 文档角色和后端分类目录一致。

任一检查失败时，本次文档任务失败，原始标准输出和错误输出保留在 workspace 日志目录中，不写入不符合契约的最终文档。

## 9. 与 Benchmark 的对应关系

| Benchmark 能力 | 主要证据章节 |
|---|---|
| 顶层目标定位 | 快速任务导航、系统分层与模块地图 |
| 子系统定位 | 子模块导航、故障现象导航 |
| 信道业务理解 | 端到端业务流程、输入输出与数据契约 |
| 代码定位 | 源码地图、执行流程与调用链 |
| 接口和数据理解 | 入口出口与接口契约、数据结构与字段语义、APIReference |
| 时序分析 | 状态、HARQ与时序；状态、时序与资源生命周期 |
| 故障定位 | 故障定位决策树、异常路径与故障定位 |
| 修改规划 | 开发任务路由、修改指南与影响分析 |
| 可验证性 | 测试与验证、证据限制 |

因此，后续评测应检查文档是否提高代码定位、调用链恢复、故障诊断和修改规划能力，而不应只评价语言流畅度或篇幅。
